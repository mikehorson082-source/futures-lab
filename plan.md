## 1. 📥 Инфраструктура и загрузка данных (Этап 0 по CLAUDE.md)

### 1.1 Инициализация таблиц и гипертаблицы
* **Команда:**
  ```bash
  .venv/bin/python -m db.init_timescale
  ```
* **Файл:** `db/init_timescale.py`
* **Описание:** Создаёт (пересоздаёт) `futures_roots`, `futures_contracts`,
  гипертаблицу `futures_candles` (1M свечи) и continuous aggregates
  `futures_candles_m15/h1/1d` с политикой сжатия для фьючерсных данных.
* ⚠️ Пересоздаёт `futures_candles*` с нуля (`DROP ... CASCADE`) — не
  запускать повторно после того, как в БД накопится история свечей, если
  не собираешься перекачивать её заново.

### 1.2 Загрузка root-серий и контрактов
* **Команда:**
  ```bash
  .venv/bin/python -m db.sync_contracts
  ```
* **Файл:** `db/sync_contracts.py`
* **Описание:** Тянет полный список фьючерсов через T-Invest API
  (`INSTRUMENT_STATUS_ALL`, чтобы увидеть истёкшие контракты), фильтрует по
  точному `basic_asset` под 4 отслеживаемые root-серии (`SBERF`, `CNYRUBF`,
  `IMOEXF`, `BR` — правила фильтрации и их обоснование см. в `ROOT_SERIES`
  в начале файла) и пишет через UPSERT в `futures_roots` /
  `futures_contracts`.
* **Идемпотентен:** можно перезапускать в любой момент — существующие
  строки обновятся, новых дублей не будет. Чтобы добавить новую серию
  (например, золото) — дописать запись в `ROOT_SERIES` и перезапустить.
* **Текущее состояние в БД (на 2026-08-28):** 155 контрактов, 4 серии
  (SBERF — 26, CNYRUBF — 24, IMOEXF — 29, BR — 76).

### 1.3 Загрузка истории свечей
* **Команда:**
  ```bash
  .venv/bin/python -m db.sync_candles_zip
  ```
* **Файл:** `db/sync_candles_zip.py`
* **Описание:** Скачивает годовые ZIP-архивы 1M свечей (по умолчанию
  2022–2026, граница режимного сдвига — см. CLAUDE.md) для каждого
  контракта из `futures_contracts`, распаковывает в памяти и пишет
  пакетно (UPSERT) в `futures_candles`. Пропускает уже загруженные
  год+figi (`skip_existing=True`).
* **Оптимизация:** годы-кандидаты пересекаются с реальной жизнью контракта
  (`first_trade_date`…`expiration_date`) перед запросом — контракт, чья
  жизнь не пересекается с целевым периодом, пропускается вообще без
  обращения к API. Раньше (до фикса) запросы шли вслепую по всем годам для
  каждого контракта — 775 запросов вместо 239 реально нужных.
* **Статус: выполнено (2026-08-28).** Итог по всем 4 сериям:

  | root_symbol | контрактов с данными | всего контрактов | свечей    | диапазон дат            |
  | ----------- | -------------------- | ---------------- | --------- | ----------------------- |
  | BR          | 63                   | 76               | 2 338 721 | 2022-01-03 – 2026-08-27 |
  | CNYRUBF     | 24                   | 24               | 1 604 402 | 2022-03-23 – 2026-08-27 |
  | IMOEXF      | 26                   | 29               | 1 232 122 | 2022-01-03 – 2026-08-27 |
  | SBERF       | 22                   | 26               | 1 401 586 | 2022-01-03 – 2026-08-27 |

  **Итого: 6 576 831 свечей 1M.** Этап 0 (инфраструктура) закрыт.

### 1.4 Обновление календаря торговых дней
* **Команда:**
  ```bash
  .venv/bin/python -m db.sync_calendar
  ```
* **Файл:** `db/sync_calendar.py`
* **Описание:** Строит `is_trading_day` в `trading_schedules` по факту
  наличия свечей в `futures_candles` (объединение всех отслеживаемых
  серий), сверяет с ISS `dailytable` и двумя датами смены режима биржи
  как assert-проверками — это только отчёт, календарь не переопределяет.
  Подробности решения — раздел 7.
* **Идемпотентен**, но зависит от актуальности свечей: запускать
  **после** 1.3 (`db.sync_candles_zip`), иначе не увидит новые торговые
  дни — календарь строится из свечей, а не наоборот.
* **Статус: выполнено (2026-08-31).** 1700 дней (2022-01-03…2026-08-29),
  74.4% торговых, обе проверки ✅.

### 1.5 Загрузка вспомогательных данных (курсы, ставки)
* **Команда:**
  ```bash
  .venv/bin/python -m db.sync_reference_data
  ```
* **Файл:** `db/sync_reference_data.py`
* **Описание:** Загружает спот-курсы и макроэкономические данные,
  которые понадобятся для анализа базиса фьючерсов:
  * **Спот-курс CNY/RUB** — MOEX ISS, инструмент `CNYRUB_TOM` на борде
    `CETS`. Используется в Этапе 1 (анализ базиса валютного контракта).
  * **Ключевая ставка ЦБ РФ** — SOAP-сервис `cbr.ru/DailyInfoWebServ`.
    Необходима для расчёта теоретического базиса через паритет ставок.
  * **Ставка Китая (SHIBOR 1Y)** — через `akshare`, дневная, без пропусков.
    Используется в Этапе 1 для уточнения паритета ставок (формула с делением
    на ставку Китая). Подробности про загрузку и сравнение с альтернативными
    источниками — раздел 9.6.
* **Идемпотентен:** UPSERT, не дублирует строки.
* **Статус: выполнено (2026-09-01).** Данные загружены в
  `currency_rates` (1183 строк, 2022-01-03…2026-08-31), `cbr_key_rate`
  (1184 строк, 2022-01-03…2026-09-01) и `foreign_key_rates` (SHIBOR 1Y,
  1185 строк, 2022-01-04…2026-09-01). Подробности — раздел 9.

### 1.6 Построение баров и признаков
* **Команда:**
  ```bash
  .venv/bin/python -m scripts.build_bars --root CNYRUBF  # для информации
  .venv/bin/python -m scripts.build_features --root CNYRUBF
  ```
* **Файлы:** `processing/bars.py`, `processing/features.py`, `scripts/build_bars.py`, `scripts/build_features.py`
* **Описание:** Строит dollar bars и вычисляет признаки на основе загруженных данных:
  * **Бары** — накопление оборота в пределах одного торгового сегмента
    (без протяжки через выходные), порог рассчитывается по среднему
    дневному обороту контракта. Результат — стандартизированные временные
    единицы вместо календарных минут.
  * **Признаки** — три группы: структурные (дни до экспирации, ранг
    контракта, доля объёма), базис (теоретический курс и отклонение),
    ценовые (логарифмическая доходность, волатильность, момент).
* **Зависимости:** требует выполнения 1.1–1.5 (БД, контракты, свечи,
  календарь, вспомогательные данные).
* **Статус: выполнено (2026-09-01).** Результат для CNYRUBF:
  * Бары: 133 709 из 1 604 402 свечей (~8.3% свёртка)
  * Признаки: таблица `data/features/CNYRUBF_bars_features.csv`
    (не в git, в `.gitignore`). Подробности — раздел 10.

## 2. 🔬 Диагностика: склейка vs пул контрактов

### 2.1 Скрипт
* **Команда:**
  ```bash
  .venv/bin/python -m scripts.diagnose_roll_splice --root CNYRUBF
  ```
* **Файл:** `scripts/diagnose_roll_splice.py`
* **Описание:** Только чтение из БД, ничего не пишет. Универсальный —
  принимает любую root-серию через `--root`. Считает две вещи:
  1. **Скачок цены на стыке контрактов** — разница close истекающего и
     следующего контракта в день реального ролла (только для контрактов,
     которые **действительно истекли**, не для ещё живых пар — это была
     методологическая ошибка в первой версии скрипта, исправлена), в
     сравнении со обычным дневным диапазоном контракта.
  2. **Концентрация объёма по дням до экспирации**, бакеты настраиваются
     через `--near-bucket-days` (по умолчанию 30/90/180).
* **Пороги — явные константы в начале файла** (не "на глаз"): скачок
  считается значимым при > `GAP_SIGNIFICANT_RATIO` (2.0x обычной дневной
  волатильности); склейка считается рискованной, если таких скачков больше
  `GAP_SIGNIFICANT_SHARE_WARNING` (20%) переходов; пул считается безопасным
  по объёму, если в последние `POOL_SAFETY_HORIZON_DAYS` (90) дней до
  экспирации сосредоточено >= `POOL_SAFETY_VOLUME_SHARE` (80%) объёма.
* **Вывод в конце вывода скрипта считается программно** из тех же чисел,
  что напечатаны построчно — воспроизводимо, без ручной дописки текста.

### 2.2 Результат по всем 4 сериям (2026-08-29)

| Серия   | Реальных переходов | Значимых скачков (>2x) | Ср. \|скачок\| | Макс. скачок | Объём за 90д до эксп. | Вывод          |
| ------- | ------------------ | ---------------------- | -------------- | ------------ | --------------------- | -------------- |
| CNYRUBF | 18                 | 39%                    | 3.15%          | 6.93%        | 91.0%                 | Пул безопаснее |
| BR      | 56                 | 23%                    | 2.85%          | 14.55%       | 99.9%                 | Пул безопаснее |
| IMOEXF  | 18                 | 44%                    | 3.32%          | 10.52%       | 95.0%                 | Пул безопаснее |
| SBERF   | 18                 | 50%                    | 4.33%          | 8.21%        | 93.3%                 | Пул безопаснее |

Вывод «пул безопаснее наивной склейки» одинаков для всех четырёх групп —
не специфика валютного риска, а похоже на общее свойство фьючерсов на MOEX

только гипотеза для последующей проверки на этапе 4.

## 3. 🗺️ Roadmap — ещё не реализовано

Ниже — план по CLAUDE.md, зафиксированный для памяти. Ничего из этого
раздела не существует в коде, не путать с разделами 1–2.

* **Архитектура моделирования — решено (2026-08-30):** пул сырых
  контрактов, без склейки в непрерывный ряд. Диагностика (раздел 2)
  прогнана на всех 4 сериях и везде указывает на пул — это уже не
  предположение по одной серии, а согласованный результат. Но это
  эвристика по фиксированным порогам, не абсолютное доказательство —
  фиксируется явно при переходе к этапу 1.
  **Важно про признаки контракта:** raw contract-id (тикер/figi) —
  **не** годится как категориальный признак, даже на одном инструменте.
  Контракт живёт ограниченное время и исчезает после экспирации — при
  выходе в продакшн модель встретит contract-id, которого не было в
  обучении (unseen category), и не сможет его использовать. Вместо
  identity контракта нужны **структурные признаки положения в
  ролл-цикле**, которые переносятся с одного контракта на другой:
  `days_to_expiration` (или нормализованное 0..1 от жизни контракта),
  ранг контракта (ближний/второй/третий), доля объёма относительно
  типичной кривой концентрации (см. раздел 2). Отдельная модель на
  инструмент (Этапы 1–4) в `root_symbol` не нуждается — он понадобится,
  только если/когда дойдём до единой модели на несколько инструментов
  сразу, и то в паре со сравнимыми между рынками величинами (проценты,
  а не абсолютные рубли).
* **Бары по обороту (dollar bars) — решено заранее, до реализации
  (2026-08-30):** при построении баров (вероятно, часть Этапа 1) бар
  **не должен переходить через выходные** — иначе на неликвидном
  контракте один бар склеит пятницу с понедельником и создаст
  искусственную асимметрию длительности бара по дням недели. Решение:
  1) фильтр по официальному календарю торговых сессий (внебиржевые
  свечи по выходным исключаются явно), 2) бар принудительно закрывается
  на границе торгового дня, даже если порог по обороту не набран.
  **Проверено на данных futures-lab (2026-08-30):** в `futures_candles`
  тот же артефакт есть и здесь — 79 222 свечи в субботу и 66 152 в
  воскресенье (~2.2% от 6.58М), при том что FORTS в воскресенье в
  принципе не торгуется. Открытый вопрос про календарь FORTS —
  **закрыт, см. раздел 7.** Итоговое решение: граница бара — разрыв
  между соседними свечами > `GAP_THRESHOLD_MINUTES = 180` (см.
  `db/calendar.py`), не даты/часы сессии. Клиринг (короткий, симметричен
  по дням недели) закрывать бар не должен — под правило и так не
  попадает, порог 180 мин заведомо больше клиринговых пауз (~5-15 мин) и
  меньше настоящих межсессионных разрывов (от ~430 мин).
* **Этап 1 — CNYRUBF:** разбор базиса (курс + разница ставок ЦБ). Начато,
  см. раздел 9 — загрузка вспомогательных данных.
* **Этап 2 — BR:** контанго/бэквордация, влияние мировых цен на нефть.
* **Этап 3 — IMOEXF:** риск на рынок целиком.
  **Кандидат на будущее (2026-08-30):** у IMOEXF тоже есть вечный
  фьючерс на MOEX (`IMOEXF`-перпетуал, второй по ликвидности после
  `CNYRUBF`-перпетуала — раздел 6), можно повторить сравнение
  "конвергенция vs funding rate" и на индексном активе, не только на
  валютном. Не начато, просто зафиксировано, чтобы не забыть идею.
* **Этап 4 — SBERF:** анализ фьючерса на отдельную акцию.
* **Этап 5 — вечные фьючерсы MOEX (CNYRUBF-перпетуал):** funding rate
  вместо конвергенции к экспирации, тот же базовый актив, что в Этапе 1
  — намеренно, чтобы менялся только механизм, а не ещё и актив (см.
  раздел 6 — там же разведка и загрузка данных).
* **Этап 6 — криптовалюты-перпетуалы:** 5 инструментов (Bitcoin, Ethereum,
  Solana, Tron, Ripple) на MOEX FORTS, номинированные в USDT. Отличаются
  от остальных Этапов: (1) не российские активы, (2) экстремальная
  волатильность (20%+ за день), (3) перпетуальный механизм funding rate,
  (4) номинирование в USDT требует переноса модели на валютную переменную.
  Разведка и определение ликвидности — см. раздел 8.
* **Сводный этап сравнения** всех кейсов.

## 4. 📚 Литература

* **Marcos López de Prado — «Advances in Financial Machine Learning» (2018).**
  Фундаментальный источник методов для финансового ML: Triple Barrier,
  Purged K-Fold с embargo, веса по uniqueness/concurrency, meta-labeling,
  MDA по кластерам признаков. Перечитать те главы, которые применяем в
  futures-lab по умолчанию (см. CLAUDE.md).
* **John C. Hull — «Options, Futures, and Other Derivatives».** Классическая
  теория самих фьючерсов: базис, contango/backwardation, cost-of-carry
  (стоимость хранения для товаров, разница ставок для валюты), конвергенция
  цены к экспирации. Отвечает на вопрос «что вообще должно происходить с
  базисом», до того как смотреть, что происходит на самом деле.
* **Ernest P. Chan — «Algorithmic Trading» / «Quantitative Trading».**
  Практическая инженерия: как строить непрерывный ряд из цепочки
  фьючерсных контрактов (back-adjustment, ratio-adjustment вместо наивной
  склейки) и какие артефакты создаёт каждый способ. Самый прицельный
  источник под вопрос «склейка или пул контрактов».
* **Larry Harris — «Trading and Exchanges».** Микроструктура рынков —
  откуда берётся ликвидность, почему у дальних контрактов объём тонкий.
  Пригодится для диагностики концентрации объёма по времени до экспирации.


## 5. Мысли для статьи

1. **Приоритет подготовки данных над моделью в финансовом ML:**
   * **Сырые свечи «в лоб» не работают:** без нормализации и масштабирования признаков модель учит случайный шум.
   * **Целостность рядов:** критично отсутствие пропусков и аномалий (например, пауза торгов на Мосбирже в 2022 г. ломает обучение).
   * **Альтернативные бары (де Прадо):** стандартные тайм-бары (5м) уступают барам по объёму, объёму в валюте или тикам.
   * **Ключевой инсайт:** если данные сформированы, очищены и размечены правильно, обучение модели и получение результата превращается в стандартную инженерно-техническую задачу.


## 6. 🔁 Вечные фьючерсы MOEX (Этап 5) — разведка и загрузка

### 6.1 Что вскрылось

Старый фильтр в `db/sync_contracts.py` отбрасывал всё с
`expiration_date.year >= 2090` как "синтетику". На деле там были
смешаны две разные вещи:

1. **Настоящие вечные фьючерсы MOEX FORTS** — та же биржа и класс

## 7. 📅 Календарь торговых дней FORTS — расследование и решение (2026-08-31)

### 7.1 С чего начали

Открытый вопрос из раздела 3: нужно разобраться с календарём сессий FORTS.
Расследование сильно разрослось — по ходу всплыло намного больше, чем
просто "другие часы".

### 7.2 Что выяснилось про сам рынок

* **ДСВД (Дополнительная сессия выходного дня) — официальная биржевая
  сессия**, не брокерская синтетика. Подтверждено дважды независимо: (1)
  метаданные инструмента через T-Invest API (`exchange='forts_futures_weekend'`,
  `real_exchange=1`, `class_code=SPBFUT` — то же самое у будних и
  выходных контрактов, не `spb_future`/`real_exchange=0`, как у
  брокерских "Neo"-перпетуалов из раздела 6.1); (2) официальный
  пресс-релиз MOEX и страница
  [moex.com/derivatives/weekend-session](https://www.moex.com/derivatives/weekend-session).
* **Режим сессии менялся минимум 5 раз за 2025-2026 год:**

  | Дата       | Изменение                                                                                                                                                        |
  | ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | 2025-08-16 | Запуск ДСВД (все фьючерсы кроме валютных), сб/вс 09:50-19:00 МСК                                                                                                 |
  | 2026-03-23 | Отмена внутридневных клиринговых перерывов ("единая сессия"), клиринг перенесён на конец дня; вечерняя сессия стала относиться к текущему дню, а не к следующему |
  | 2026-07-14 | Будни: старт сдвинут с 08:50 на 06:50 МСК                                                                                                                        |
  | 2026-07-18 | Валютные фьючерсы (CNYRUBF) допущены к ДСВД                                                                                                                      |

  При таком темпе изменений жёсткие константы времени сессии по эрам
  были бы гарантированно устаревающим решением.
* **~25% выходных дней после запуска ДСВД — без торгов вообще**
  (проверено на полной истории 16.08.2025-29.08.2026: 27 из 109 дней),
  повторяется примерно раз в 3-6 недель. Официального объяснения не
  нашли — `dailytable` (см. ниже) отражает только 3 самые свежие даты из
  27, остальные нигде не задокументированы.

### 7.3 Ни один справочник не даёт полной истории — только свечи

* T-Invest `trading_schedules` — не смотрит в прошлое вообще (`from`
  can't be less than the current date), только на ~14 дней вперёд.
* ISS `engines/futures.json` → `session_schedule` — тоже только
  "сегодня", параметр `date=` в запросе полностью игнорируется.
* ISS `engines/futures.json` → `dailytable` — историчен (с 2018 года),
  полезен для сверки, но **неполон**: не отразил нерабочую субботу
  01.08.2026, зато случайно поймал 3 других; и наоборот, 01.05.2026
  помечен нерабочим, хотя по свечам был полноценный торговый день
  (2542 свечи BR, обычный дневной паттерн 06:59-20:49 UTC).

Вывод, зафиксированный как принцип: **свечи — основа, задокументированные
факты (даты режима, `dailytable`) — проверка результата (assert), а не
источник данных для его построения.** Причина: свечи ни разу за всё
расследование не подвели, справочники — каждый по-своему подвели.

### 7.4 Свечи — действительно биржевые, не брокерская синтетика

Отдельно проверили опасение "а не дилерские ли это котировки Т-Банка,
раз торгуют по выходным": в gRPC `GetCandles` есть поле `candle_source`
(`CANDLE_SOURCE_EXCHANGE` vs `CANDLE_SOURCE_DEALER_WEEKEND`). Проверили
выборочно, специально в местах, где дилерские котировки вероятнее всего
(первый день каждого режима — 16.08.2025 и 18.07.2026, когда
маркетмейкеры ещё могли не подключиться): везде и всегда
`CANDLE_SOURCE_EXCHANGE`, ни одной дилерской. **Оговорка:** это поле
есть только в gRPC, не в ZIP-архивах (`history-data`), которыми грузится
основная история — выборочная проверка, не сплошной аудит всех 6.5 млн
строк.

**Решено (2026-08-31, уточнено):** колонка `candle_source SMALLINT`
добавлена в `futures_candles` (`db/models.py`, `db/init_timescale.py` —
неразрушающий `ALTER TABLE`, данные не пересоздавались). Значения по
`t_tech.invest.schemas.CandleSource` (1=EXCHANGE, 2=DEALER_WEEKEND,
3=INCLUDE_WEEKEND). Все существующие 7 298 580 строк (загружены из ZIP)
имеют `candle_source IS NULL` — источник для них не проставлен построчно,
доверие к ним основано на выборочной проверке выше, не на этом поле.
Колонка — задел под будущую догрузку свежих данных через gRPC
`GetCandles` (загрузчик ещё не написан), где источник можно будет
проставлять честно на каждую строку.

**Уточнено (2026-08-31):** добавлена ещё одна колонка —
`ingest_source VARCHAR(16)` (`db/models.py`, `db/init_timescale.py`) —
не про биржу, а про то, каким из наших загрузчиков записана строка
(`'zip'` — `db/sync_candles_zip.py`, `'grpc'` — будущая догрузка).
Все существующие строки размечены задним числом: `ingest_source='zip'`,
`candle_source=1` (EXCHANGE) — решение принято сознательно (см. 7.4),
не автоматически. Технически: массовый `UPDATE` на 7.3 млн строк упёрся
в защитный лимит TimescaleDB (`max_tuples_decompressed_per_dml_transaction`,
дефолт 100 000) — снят только на время сессии соединения (`SET`, не
`ALTER SYSTEM`), обновление прогнано по годам. После — ожидаемый всплеск
autovacuum на затронутых чанках, не сбой.

### 7.5 Итоговое решение — граница дня по разрыву, не по дате/часам

Рассматривали три подхода: (1) жёсткие константы по эрам, (2) дата с
переводом в МСК + конфиг с часами сессии, (3) разрыв между соседними
свечами. Выбран **(3)**.

Почему не (1): требует ручной правки кода при каждой смене режима биржи
(см. 7.2 — уже 5 раз за год).

Почему не (2): дата+МСК чинит проблему часового пояса, но конфиг с
часами сессии упирается в ту же проблему "нескольких эр", что и
вариант (1) — плюс жёсткий разрез по полуночи МСК не адаптируется, если
биржа когда-нибудь уйдёт в круглосуточную торговлю (риск не
гипотетический: биржа уже дважды за год расширяла часы в эту сторону).

**Порог `GAP_THRESHOLD_MINUTES = 180` минут** (см. `db/calendar.py`)
подобран по фактическому распределению разрывов между соседними
минутными свечами (2022-2026, все 5 серий): обычный внутридневной шум
почти всегда ≤15-20 минут, редкие исключения (до ~215 мин) — все
разобраны и объясняются реальными событиями (24.02.2022 — начало СВО;
25.03-18.04.2022 — первые недели после открытия биржи; 13.09.2023,
240 мин одновременно во всех 5 сериях — похоже на общерыночную
техническую паузу, не исследовано отдельно). Настоящие межсессионные
разрывы начинаются от ~430 минут. Между ~215 и ~430 — пустая зона,
конкретное число порога внутри неё не критично.

Проверка на реальных данных подтвердила: с этим порогом
пятница/суббота-ДСВД/воскресенье-ДСВД/понедельник расходятся на 4
отдельных сегмента сами, без ручной привязки к тому, что сама биржа
официально считает выходные "частью следующего понедельника" — этот
вопрос вообще не пришлось решать.

Отдельно обсудили и решили: **технический сбой биржи на несколько
часов посреди буднего дня тоже должен закрывать бар** — это то же
самое "накопить оборот физически невозможно", что и у выходных, и
13.09.2023 (раздел выше) — уже наблюдаемый пример именно такого случая,
пойманный порогом корректно.

### 7.6 Реализация

* [db/models.py](db/models.py) — модель `TradingSchedule`
  (`date`, `weekday`, `is_trading_day`).
* [db/sync_calendar.py](db/sync_calendar.py) — строит `is_trading_day`
  по свечам (объединение всех отслеживаемых серий), сверяет с ISS
  `dailytable` (отчёт о расхождениях, не переопределяет) и с двумя
  датами смены режима как assert-проверками (запуск ДСВД, допуск
  валюты). Прогнан на боевой БД: 1700 дней (2022-01-03…2026-08-29),
  74.4% торговых, обе проверки ✅.
* [db/calendar.py](db/calendar.py) — `get_trading_day_segments(root_symbol,
  gap_threshold_minutes=180)`: SQL с оконными функциями (`LAG` + кумулятивная
  сумма), возвращает непрерывные отрезки торговли. Готово к использованию
  в будущей реализации dollar bars.

## 9. 💹 Этап 1 — CNYRUBF: вспомогательные данные для базиса (2026-09-01)

### 9.1 Теория

Базис валютного фьючерса разбирается через паритет процентных ставок
(covered interest rate parity, Hull): теоретическая цена фьючерса

```
F_theory = S × (1 + r_RUB × T/365) / (1 + r_CNY × T/365)
```

где `S` — спот-курс, `T` — дней до экспирации, `r_RUB`/`r_CNY` — безрисковые
ставки. `basis = F_actual − F_theory`. **Решено (2026-09-01):** на первом
проходе используем только `r_RUB` (ключевая ставка ЦБ), без китайской
ставки (SHIBOR) — упрощение сознательное: юаневые ставки низкие и
относительно стабильные, основная волатильность базиса ожидается с
рублёвой стороны. Если модель без китайской ставки объяснит базис плохо —
это само по себе результат, а не повод считать шаг проваленным.

### 9.2 Новый общий файл вспомогательных данных

[db/sync_reference_data.py](db/sync_reference_data.py) — по просьбе
пользователя единая точка для всех загрузок, которые не являются ни
фьючерсным контрактом, ни свечой (курсы, ставки; в будущем — другие
подобные ряды). `db/sync_calendar.py` **не тронут** — уже работает и
задокументирован в разделе 7, объединять не стали.

**Источники (оба публичные, без токена):**
* **Спот-курс CNY/RUB** — MOEX ISS, инструмент `CNYRUB_TOM`, борд `CETS`.
  Торги юанем на MOEX **не прерывались** — весь период
  2022-01-03…2026-08-31 непрерывен, биржевой ряд можно использовать
  напрямую как исторический источник курса CNY/RUB.
* **Ключевая ставка ЦБ РФ** — SOAP-сервис `cbr.ru/DailyInfoWebServ`,
  метод `KeyRate`. Отдаёт ряд **по датам действия ставки**, не объявления
  решения (решение объявляется на несколько дней раньше, чем начинает
  действовать — дата объявления была бы утечкой из будущего). Важно:
  использовать дату действия ставки, а не дату объявления.
* Обе загрузки — через `curl` в subprocess с ретраями, не `urllib`
  напрямую: в этом окружении прямой `urllib` к внешним хостам стабильно
  уходит в таймаут (та же особенность, что у `sync_calendar.py` и
  `sync_candles_zip.py`, зафиксирована там же).
* Хранение — в БД (`currency_rates`, `cbr_key_rate`). В futures-lab с самого
  начала принято решение всё держать в TimescaleDB (см. CLAUDE.md).

### 9.6 Ставка Китая — проверка гипотезы про дрейф знака (2026-09-01)

**Источник ставки Китая — прошли через три варианта, прежде чем
остановиться:**
1. API Ninjas (изначально предложенный пользователем, `.env: API_NINJAS`)
   — на бесплатном плане отдаёт только ТЕКУЩУЮ ставку без истории,
   `/v2/interestratehistorical` требует Premium (проверено явно:
   `{"error": "This API endpoint is only available to premium
   subscribers."}`).
2. FRED (`INTDSRCNM193N`, "Discount Rate for China") — бесплатно, но
   месячная гранулярность, ряд обрывается на 2025-06, и почти не меняется
   (2.70%…3.33% за 3.5 года) — первая проверка на нём дала прирост
   объяснения, растущий по годам (см. историю ниже), что оказалось
   артефактом покрытия данных, а не сигналом.
3. **`akshare`** (по прямой просьбе пользователя) — два ряда, оба через
   `sync_foreign_key_rate()` в таблицу `foreign_key_rates`
   (`db/sync_reference_data.py`):
   * **SHIBOR 1Y** — дневная, 2022-01-04…2026-09-01, **без единого
     пропуска**. Используется по умолчанию в `compute_basis.py`.
   * **LPR 1Y** — по датам объявления решений, ~раз в месяц, до
     2026-08-20. Загружена, но не задействована по умолчанию — сохранена
     на будущее (второй `series` под тем же `country='CN'`, схема
     `foreign_key_rates` рассчитана на несколько одновременных рядов).

   ⚠️ **Тяжёлая зависимость**: `akshare` тянет `pandas`, `numpy`, `lxml`,
   `beautifulsoup4`, `curl-cffi` и `mini-racer` (встроенный движок JS —
   для обхода антибот-защиты китайских сайтов-агрегаторов). Осознанно
   принято ради качества данных (реальная дневная ставка вместо почти
   константы), не потому что зависимость лёгкая.

`scripts/compute_basis.py` считает **обе версии формулы одновременно**
(`rub_only` — прежняя, `full` — с делением на ставку Китая) и сравнивает
по годам экспирации контракта (SHIBOR 1Y, дневная):

| Год эксп. | rub_only mean | full(+SHIBOR) mean |           Δ |
| --------- | ------------: | -----------------: | ----------: |
| 2022      |       +1.679% |            +2.094% | +0.415 п.п. |
| 2023      |       -0.329% |            +0.705% | +1.034 п.п. |
| 2024      |       -2.799% |            -1.177% | +1.622 п.п. |
| 2025      |       -4.873% |            -3.551% | +1.322 п.п. |
| 2026      |       -3.336% |            -2.090% | +1.246 п.п. |
| 2027      |       -5.583% |            -3.907% | +1.676 п.п. |

**Итог более надёжный, чем с FRED, и он усиливает вывод, а не меняет
его.** С реальной дневной SHIBOR (упавшей за период с 2.7% до 1.48% —
не константа) прирост объяснения по годам почти ровный (+0.4…+1.7 п.п.),
**не растёт монотонно**, как было с почти-константным FRED — то есть
растущий прирост в версии с FRED был артефактом покрытия данных
(меньше наблюдений с большим T у ранних контрактов), а не реальным
сигналом. При этом сам дрейф знака (с положительного в 2022-2023 на
устойчиво отрицательный к 2024-2027, размах ~6 п.п. даже после поправки)
**никуда не делся** и с настоящей, ежедневно обновляемой ставкой. Это
усиливает гипотезу: остаточный дрейф — не про то, что мы использовали не
ту ставку Китая, а про что-то ещё, вне модели паритета процентных
ставок (вероятный кандидат — растущая инфраструктурная премия за
санкционный риск в CNY/RUB: капитальные ограничения, стоимость
хеджирования). Не проверено, честно оставлено как открытый вопрос.

дойдём до обучения модели, порог нужно

### 10.2 Признаки

[processing/features.py](processing/features.py) — три группы, один бар =
одна строка, порядок разработки структурные → базис → ценовые (по просьбе
пользователя):

* **Структурные** (замена raw contract-id, раздел 3): `days_to_expiration`,
  `life_fraction_remaining` (0..1, нормировано на полную жизнь контракта),
  `contract_rank` (1 = ближайший к экспирации живой контракт), `volume_share`
  (доля дневного оборота контракта в обороте всех живых контрактов серии —

* **Базис** — только для root-серий с записью в `ROOT_TO_SPOT_PAIR`

  [scripts/compute_basis.py](scripts/compute_basis.py) напрямую (не
  задублированы), но `F_actual` берётся из close бара, не дневного
  закрытия.
* **Ценовые**, строго внутри контракта (без протяжки через ролл):
  `log_return_1`, `volatility_20` (pstdev за 20 баров), `momentum_10`
  (сумма за 10 баров). Минимальный стартовый набор, не индикаторный
  зоопарк — расширяется по мере необходимости.

**Найден и исправлен баг на границе экспирации**: фильтр "живых" контрактов
использовал строгое `expiration_date > d`, из-за чего бары **в сам день
экспирации** (до 78 баров на контракт — день экспирации активно
торгуется, не тонкий) оставались без `contract_rank`/`volume_share`.
Исправлено на `>=`. Пойман честно через проверку покрытия признаков
(доля non-null по колонкам), не молча.

## 12. ✂️ Этап 1 — train/test с purge/embargo (2026-09-01)

[processing/splitting.py](processing/splitting.py) — один разрез по
времени (не k-fold), с двумя механизмами защиты от утечки (López de Prado,
раздел 4):
* **Purge** — из train убираются строки, чьё окно предсказания (`t1`)
  залезает в test. Прямое следствие нахлёста меток (раздел 11): без purge
  train "видел" бы часть test-будущего.
* **Embargo** — сверх purge, из train убирается буфер перед границей test
  (доля от общего временного диапазона, по умолчанию 1%) — подстраховка от
  автокорреляции, которую точная граница окна метки не ловит.

Разрез — **по календарному времени**, не по числу строк: строки
неравномерно плотные (в поздние годы больше живых контрактов -> больше
баров в день), разрез по числу строк сместил бы test непропорционально.

**Результат** ([scripts/build_split.py](scripts/build_split.py), CNYRUBF,
2026-09-01, `test_fraction=0.2`, `embargo_fraction=0.01`):

| | train | test |
|---|---:|---:|
| строк | 87 272 | 43 928 |
| период | 2022-04-06 … 2025-09-29 (`t1`) | 2025-10-10 … 2026-08-27 |
| target=1 | 35.4% | 36.6% |

Purge убрал 12 строк, embargo — 1537. Инвариант проверен явно (`assert`
в скрипте): `max(t1)` по train строго меньше границы test — OK.

**Наблюдение, не баг:** test получился 33.5% строк при заказанных 20% по
времени — ожидаемо при разрезе по календарю, а не по строкам (см. выше
про плотность баров в поздние годы). Доля `target=1` почти одинакова на
train/test — разметка не искажена на границе разреза.

⚠️ **Числа выше устарели** — весь пайплайн (бары → признаки → разметка →
разрез) пересчитан после раздела 13 (train-only порог dollar bars),
актуальные цифры там. Оставлено для истории решения, не как текущее
состояние `data/features/CNYRUBF_train.csv` / `_test.csv`.

**Дальше:** две провизорности всё ещё открыты и теперь можно закрыть —
(1) порог dollar bars пересчитать только по train (раздел 10.1), (2) вес
примеров по uniqueness/нахлёсту меток (раздел 11).

## 13. 🔧 Этап 1 — закрытие двух провизорностей (2026-09-01)

### 13.1 Порог dollar bars по train — первая попытка и найденный побочный эффект

Первая версия (`calibrate_thresholds` в `processing/bars.py`, теперь
удалена): один порог на контракт = средний дневной оборот контракта
**только по дням до `split_time`** (раздел 12), с fallback на общий по
серии порог для контрактов без единого train-дня.

**Побочный эффект, найденный при прогоне** (не увидели заранее при
планировании): число баров выросло с 133 709 до 433 854 (×3.2). У
контрактов, чья ликвидная фаза (последние дни перед экспирацией — раздел
2, концентрация объёма) приходится на test-период (например, CRU6, эксп.
2026-09), "свой" train — это только тонкое начало жизни. Порог,
откалиброванный по тонкому началу и применённый ко всей жизни контракта,
давал вместо целевых ~30 баров/день — **250-275**: у CRU6, CRM6, CRH6,
CRZ6 бар резался в разы чаще именно на самом ликвидном участке. Формальной
утечки не было (порог не использовал будущий оборот ЭТОГО контракта), но
побочный эффект был хуже утечки: датасет стал сильно перекошен (несколько
контрактов по 100К+ баров против ~8К у остальных), а сама идея dollar bars
(«одинаковая активность на бар») — нарушена именно там, где контракт
наиболее ликвиден.

Разобрано с пользователем явно, не продавлено молча (см. CLAUDE.md, п.4).
Выбрано решение — кривая порога по бакетам, не число на контракт (ниже).

### 13.2 Решение — порог как функция от days_to_expiration

`calibrate_threshold_curve` + `thresholds_for_contract`
([processing/bars.py](processing/bars.py)): порог — не одно число на
контракт, а **кривая по тем же бакетам days_to_expiration**, что в
`scripts/diagnose_roll_splice.py` (раздел 2): `<=7д`, `7-30д`, `30-90д`,
`90-180д`, `>180д`. Значение бакета — средний дневной оборот **всех**
контрактов серии на этом расстоянии до экспирации, посчитанный только по
train-периоду (пул, не по одному контракту). Молодой контракт, чья
собственная ликвидная фаза ещё не наступила, получает порог из чужого —
уже отторговавшего — опыта на том же расстоянии до экспирации, а не
растянутую на всю жизнь свою тонкую историю. Пустой бакет (в train не
нашлось ни одного дня — не должно случаться при разумном `test_fraction`)
заполняется ближайшим непустым соседом.

`build_dollar_bars` теперь принимает порог как список (по свече), не
только число — старый режим (`scripts/build_bars.py`, диагностика
механики, не чувствительна к утечке) не тронут.

**Результат по CNYRUBF** (2026-09-01, `--test-fraction 0.2`):

| Бакет | Порог (₽) |
|---|---:|
| <= 7д | 1 359 741 |
| 7-30д | 1 294 468 |
| 30-90д | 1 179 747 |
| 90-180д | 130 073 |
| > 180д | 292 |

Бары/день по проблемным контрактам после фикса: CRU6 36.5, CRZ6 41.6,
CRM6 32.9 — все в разумных пределах вокруг целевых 30, вместо 250-275.
Итого 125 555 баров (было 133 709 на исходной, «протекающей» калибровке —
близко, в отличие от промежуточных 433 854 с плоским train-only порогом).

### 13.3 Вес по uniqueness (компенсация нахлёста меток, раздел 11)

`compute_uniqueness_weights` ([processing/labeling.py](processing/labeling.py),
AFML гл. 4): каждой метке — вес = среднее по её окну (`event_idx`..`exit_idx`)
от `1/concurrency(t)`, где `concurrency(t)` — сколько меток того же
контракта одновременно активны в момент `t`. Метка, которая почти всегда
перекрывается с 7-8 соседями (наша типичная ситуация), получает вес
~0.1-0.15 вместо того, чтобы считаться независимой строкой наравне с
редкой, действительно уникальной меткой. Сохраняется как колонка
`sample_weight` в размеченном датасете — не нормализован (среднее = 1)
специально: нормализация должна происходить на train-подмножестве в
момент обучения, не глобально (иначе тоже лёгкая утечка через test).

**Результат** ([scripts/build_labels.py](scripts/build_labels.py),
CNYRUBF): mean=0.226, median=0.210, min=0.048, max=0.929. Справочная
проверка: mean overlap 8.6 -> грубая оценка `1/(8.6+1) ≈ 0.104` — фактический
mean-вес (0.226) выше, что математически ожидаемо (среднее от `1/x` по
неравенству Йенсена не равно `1/среднее(x)` для выпуклой `1/x`), не ошибка.
