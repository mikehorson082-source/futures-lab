## 0. ⚙️ Подготовка окружения

### 0.1 Создание venv
* **Команда:**
  ```bash
  uv venv --python 3.14 .venv
  ```
* **Описание:** Своё окружение внутри `futures-lab`, независимые зависимости.

### 0.2 Установка зависимостей
* **Команда:**
  ```bash
  source .venv/bin/activate
  uv pip install -r requirements.txt --extra-index-url https://opensource.tbank.ru/api/v4/projects/238/packages/pypi/simple
  ```
* **Файл:** `requirements.txt`
* ⚠️ **Важно:** `t-tech-investments` сейчас в карантине на PyPI
  (`project-status: quarantined`) — без `--extra-index-url` на официальный
  индекс Т-Банка пакет не найдётся вообще ни в какой версии.

### 0.3 Переменные окружения
* **Файл:** `.env`
* **Описание:** `TINKOFF_SANDBOX_TOKEN` — реальный рабочий токен T-Invest API
  (несмотря на слово "sandbox" в названии — это терминология про режим
  счёта, а не про качество рыночных данных). `TINKOFF_READONLY_TOKEN` —
  незаполненная заглушка, не используется. Опционально `DB_HOST`,
  `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD` — переопределяют дефолты
  в `db/database.py` (по умолчанию: `localhost:5432`, база `futures_lab`).

## 1. 📥 Инфраструктура и загрузка данных (Этап 0 по CLAUDE.md)

### 1.1 Инициализация таблиц и гипертаблицы
* **Команда:**
  ```bash
  .venv/bin/python -m db.init_timescale
  ```
* **Файл:** `db/init_timescale.py`
* **Описание:** Создаёт (пересоздаёт) `futures_roots`, `futures_contracts`,
  гипертаблицу `futures_candles` (1M свечи) и continuous aggregates
  `futures_candles_m15/h1/1d` с политикой сжатия для фьючерсных данных.
* ⚠️ Пересоздаёт `futures_candles*` с нуля (`DROP ... CASCADE`) — не
  запускать повторно после того, как в БД накопится история свечей, если
  не собираешься перекачивать её заново.

### 1.2 Загрузка root-серий и контрактов
* **Команда:**
  ```bash
  .venv/bin/python -m db.sync_contracts
  ```
* **Файл:** `db/sync_contracts.py`
* **Описание:** Тянет полный список фьючерсов через T-Invest API
  (`INSTRUMENT_STATUS_ALL`, чтобы увидеть истёкшие контракты), фильтрует по
  точному `basic_asset` под 4 отслеживаемые root-серии (`SBERF`, `CNYRUBF`,
  `IMOEXF`, `BR` — правила фильтрации и их обоснование см. в `ROOT_SERIES`
  в начале файла) и пишет через UPSERT в `futures_roots` /
  `futures_contracts`.
* **Идемпотентен:** можно перезапускать в любой момент — существующие
  строки обновятся, новых дублей не будет. Чтобы добавить новую серию
  (например, золото) — дописать запись в `ROOT_SERIES` и перезапустить.
* **Текущее состояние в БД (на 2026-08-28):** 155 контрактов, 4 серии
  (SBERF — 26, CNYRUBF — 24, IMOEXF — 29, BR — 76).

### 1.3 Загрузка истории свечей
* **Команда:**
  ```bash
  .venv/bin/python -m db.sync_candles_zip
  ```
* **Файл:** `db/sync_candles_zip.py`
* **Описание:** Скачивает годовые ZIP-архивы 1M свечей (по умолчанию
  2022–2026, граница режимного сдвига — см. CLAUDE.md) для каждого
  контракта из `futures_contracts`, распаковывает в памяти и пишет
  пакетно (UPSERT) в `futures_candles`. Пропускает уже загруженные
  год+figi (`skip_existing=True`).
* **Оптимизация:** годы-кандидаты пересекаются с реальной жизнью контракта
  (`first_trade_date`…`expiration_date`) перед запросом — контракт, чья
  жизнь не пересекается с целевым периодом, пропускается вообще без
  обращения к API. Раньше (до фикса) запросы шли вслепую по всем годам для
  каждого контракта — 775 запросов вместо 239 реально нужных.
* **Статус: выполнено (2026-08-28).** Итог по всем 4 сериям:

  | root_symbol | контрактов с данными | всего контрактов | свечей    | диапазон дат            |
  | ----------- | -------------------- | ---------------- | --------- | ----------------------- |
  | BR          | 63                   | 76               | 2 338 721 | 2022-01-03 – 2026-08-27 |
  | CNYRUBF     | 24                   | 24               | 1 604 402 | 2022-03-23 – 2026-08-27 |
  | IMOEXF      | 26                   | 29               | 1 232 122 | 2022-01-03 – 2026-08-27 |
  | SBERF       | 22                   | 26               | 1 401 586 | 2022-01-03 – 2026-08-27 |

  **Итого: 6 576 831 свечей 1M.** Этап 0 (инфраструктура) закрыт.

### 1.4 Обновление календаря торговых дней
* **Команда:**
  ```bash
  .venv/bin/python -m db.sync_calendar
  ```
* **Файл:** `db/sync_calendar.py`
* **Описание:** Строит `is_trading_day` в `trading_schedules` по факту
  наличия свечей в `futures_candles` (объединение всех отслеживаемых
  серий), сверяет с ISS `dailytable` и двумя датами смены режима биржи
  как assert-проверками — это только отчёт, календарь не переопределяет.
  Подробности решения — раздел 3 журнала.
* **Идемпотентен**, но зависит от актуальности свечей: запускать
  **после** 1.3 (`db.sync_candles_zip`), иначе не увидит новые торговые
  дни — календарь строится из свечей, а не наоборот.
* **Статус: выполнено (2026-08-31).** 1700 дней (2022-01-03…2026-08-29),
  74.4% торговых, обе проверки ✅.

### 1.5 Загрузка вспомогательных данных (курсы, ставки)
* **Команда:**
  ```bash
  .venv/bin/python -m db.sync_reference_data
  ```
* **Файл:** `db/sync_reference_data.py`
* **Описание:** Загружает спот-курсы и макроэкономические данные,
  которые понадобятся для анализа базиса фьючерсов:
  * **Спот-курс CNY/RUB** — MOEX ISS, инструмент `CNYRUB_TOM` на борде
    `CETS`. Используется в Этапе 1 (анализ базиса валютного контракта).
  * **Ключевая ставка ЦБ РФ** — SOAP-сервис `cbr.ru/DailyInfoWebServ`.
    Необходима для расчёта теоретического базиса через паритет ставок.
  * **Ставка Китая (SHIBOR 1Y)** — через `akshare`, дневная, без пропусков.
    Используется в Этапе 1 для уточнения паритета ставок (формула с делением
    на ставку Китая). Подробности про загрузку и сравнение с альтернативными
    источниками — раздел 5.6 журнала.
* **Идемпотентен:** UPSERT, не дублирует строки.
* **Статус: выполнено (2026-09-01).** Данные загружены в
  `currency_rates` (1183 строк, 2022-01-03…2026-08-31), `cbr_key_rate`
  (1184 строк, 2022-01-03…2026-09-01) и `foreign_key_rates` (SHIBOR 1Y,
  1185 строк, 2022-01-04…2026-09-01). Подробности — раздел 5 журнала.

### 1.6 Построение баров, признаков, разметки, train/test и v2-признаков

* **Команда (один запуск на весь пайплайн, финальная конфигурация
  Этапа 1 — раздел 20 журнала):**
  ```bash
  .venv/bin/python -m scripts.build_dataset --root CNYRUBF --tag _w4 \
      --horizon-bars 80 --tp-vol-mult 4.0 --sl-vol-mult 2.0
  ```
  Без `--tag`/`--horizon-bars`/`--tp-vol-mult`/`--sl-vol-mult` команда
  соберёт baseline с узкими барьерами раздела 7 журнала (`--horizon-bars 20
  --tp-vol-mult 2.0 --sl-vol-mult 1.0`, без тега в имени файлов) — эта
  конфигурация убыточна после издержек (раздел 19 журнала), брать её как
  основную для дальнейшей работы не нужно, она осталась только как
  честный baseline для сравнения. Остальные параметры — как в разделах
  6-9 журнала: `--target-bars-per-day 30`, `--min-candles 50`,
  `--test-fraction 0.2`, `--embargo-fraction 0.01`.
* **Файл:** `scripts/build_dataset.py` — вызывает по очереди четыре
  самостоятельных шага (ничего не дублирует):
  1. `scripts.build_features` (`processing/bars.py`, `processing/features.py`)
     — dollar bars (порог — кривая по бакетам days_to_expiration,
     train-only калибровка, раздел 9.2 журнала) + признаки (структурные, базис,
     ценовые, раздел 6.2 журнала) → `data/features/<root>_bars_features.csv`
     (без тега — не зависит от разметки).
  2. `scripts.build_labels` (`processing/labeling.py`) — разметка Triple
     Barrier + веса по uniqueness (раздел 7, 9.3 журнала) →
     `data/features/<root>_bars_labeled<tag>.csv`.
  3. `scripts.build_split` (`processing/splitting.py`) — train/test с
     purge/embargo (раздел 8 журнала) → `data/features/<root>_train<tag>.csv`,
     `<root>_test<tag>.csv`.
  4. `scripts.build_derived_features` (`processing/features.py`,
     `add_derived_features`) — стационарные признаки поверх готовых
     train/test (раздел 17 журнала) → `data/features/<root>_train<tag>_v2.csv`,
     `<root>_test<tag>_v2.csv`. Именно эти `_v2` файлы обучала финальная
     модель раздела 20 журнала.

  `--test-fraction` передаётся ОДИН раз на весь пайплайн и используется
  и на шаге 1 (граница train-only калибровки порога), и на шаге 3 (сам
  разрез) — при раздельном запуске шагов это нужно синхронизировать
  руками (см. предупреждения в самих скриптах), здесь синхронизировано
  автоматически. `--tag` тоже один на весь пайплайн — передаётся в шаги
  2-4, чтобы варианты разметки не затирали файлы друг друга на диске
  (раздел 20 журнала).

  Каждый шаг можно запустить и отдельно (например, пересчитать только
  разметку с другим горизонтом: `scripts.build_labels --root CNYRUBF
  --horizon-bars 30 --tag _test`) — `scripts/build_bars.py` тоже
  остаётся отдельно, это диагностика механики баров (раздел 6.1 журнала), не
  часть датасета.
* **Зависимости:** требует выполнения 1.1–1.5 (БД, контракты, свечи,
  календарь, вспомогательные данные).
* **Статус: выполнено (2026-09-01).** Финальный результат для CNYRUBF
  (`--tag _w4`, актуальные цифры — раздел 20 журнала): 123 261 бар размечен,
  нахлёст 25.8, mean вес 0.091. Шесть файлов — в `data/features/` (не в
  git, в `.gitignore`); на диске оставлены только baseline без тега и
  финальный `_w4`/`_w4_v2` вариант, промежуточные `_w8`/`_w16` из
  перебора раздела 20.1 журнала удалены как отработавшие черновики.

### 1.7 Вспомогательный инструмент — разведка новых root-серий
* **Команда:**
  ```bash
  .venv/bin/python -m scripts.explore_futures
  ```
* **Файл:** `scripts/explore_futures.py`
* **Описание:** Не часть пайплайна, не пишет в БД. Тянет через T-Invest
  API список фьючерсов (`INSTRUMENT_STATUS_BASE` — только активные
  сейчас контракты, в отличие от `sync_contracts.py`, который берёт
  `INSTRUMENT_STATUS_ALL`, включая истёкшие) и группирует по
  `basic_asset`, фильтруя по ключевым словам из словаря `TARGETS` в
  начале файла. Так были найдены 4 текущие root-серии (`SBERF`,
  `CNYRUBF`, `IMOEXF`, `BR`) перед тем, как зашить их в
  `ROOT_SERIES` (`db/sync_contracts.py`).
* **Когда пригодится:** перед стартом нового этапа, если нужен базовый
  актив, которого ещё нет в `TARGETS` — например, золото (`GLDRUBF`)
  для Этапа 2 или `GAZPF` как запасной вариант для Этапа 4. Дописать
  ключевое слово в `TARGETS` и перезапустить; найденный тикер потом
  вручную добавляется в `ROOT_SERIES`.

## 2. 🧾 Шпаргалка — как воспроизвести финальную модель и бэктест Этапа 1

Разделы 10–20 журнала (journal.md) — исследовательский журнал (что
пробовали, что не сработало и почему). Здесь — только путь к итоговому
числу раздела 20.2 журнала, без тупиков (не CatBoost, не структурные
признаки, не фильтр ликвидности — все три проверены и отброшены с
обоснованием там). Требует выполненного раздела 1 (1.1–1.5, БД).

### 2.1 Финальный датасет
```bash
.venv/bin/python -m scripts.build_dataset --root CNYRUBF --tag _w4 \
    --horizon-bars 80 --tp-vol-mult 4.0 --sl-vol-mult 2.0
```
То же, что раздел 1.6 — повторено здесь для полноты цепочки. Даёт
`CNYRUBF_train_w4_v2.csv` / `CNYRUBF_test_w4_v2.csv`, от них зависят
все шаги ниже.

### 2.2 Walk-forward внутри train — выбор модели и признаков
```bash
.venv/bin/python -m scripts.walkforward_eval --root CNYRUBF --tag _w4
```
* **Файл:** `scripts/walkforward_eval.py`. Test не открывает — сравнивает
  4 заранее зафиксированных варианта (раздел 18 журнала): v1/логрегрессия,
  v2-структ+рынок/логрегрессия, v2-только рынок/логрегрессия, v2-только
  рынок/CatBoost. Печатает mean/std/min/max AUC по 5 окнам для каждого.
* **Ожидаемый вывод:** три варианта v2 неразличимы между собой и все
  обгоняют v1; побеждает простейший — **6 рыночных признаков (`MKT` в
  коде) + логрегрессия**. CatBoost не даёт преимущества (разделы 11-15,
  18 журнала) — воспроизводится тем же прогоном, не отдельным скриптом.

### 2.3 Walk-forward внутри train — проверка торгового правила
```bash
.venv/bin/python -m scripts.backtest_walkforward --root CNYRUBF --tag _w4 \
    --min-volume-share 0
```
* **Файл:** `scripts/backtest_walkforward.py`. Тот же принцип (test не
  открывается) применён не к модели, а к правилу входа — здесь
  проверяется, что фильтр ликвидности (`--min-volume-share`) не даёт
  преимущества на `_w4` (раздел 20.1 журнала) — в отличие от раздела 19.2
  журнала, где фильтр сначала выглядел выигрышным именно потому, что был
  подобран по test.

### 2.4 Финальный прогон на test — открывается один раз
```bash
.venv/bin/python -m scripts.final_eval --root CNYRUBF --tag _w4
```
* **Файл:** `scripts/final_eval.py`. Модель (шаг 2.2 этого файла)
  обучается на всём train и проверяется на test один раз: AUC, блочный
  бутстрап 95% ДИ, AUC по 5 календарным под-периодам, precision/lift при
  пороге, выбранном на train (топ-10%). Числа — раздел 20.2 журнала,
  колонка **w4**.

### 2.5 Бэктест с издержками — тоже один раз
```bash
.venv/bin/python -m scripts.backtest --root CNYRUBF --tag _w4
```
* **Файл:** `scripts/backtest.py`. Та же модель, полный учёт: одна
  позиция за раз, вход по открытию следующего бара, издержки по спреду
  СВОЕГО контракта (оценка Roll), сравнение с безрисковой ставкой ЦБ,
  контроль на перемешанных вероятностях. `--min-volume-share` по
  умолчанию 0 (без фильтра — раздел 2.3 этого файла показал, что он не
  нужен). Результат — раздел 20.2 журнала, строки «чистая б.п./сделку» /
  «годовых».

### 2.6 Диагностические скрипты — не часть текущей цепочки

Четыре скрипта из ранней части исследования (разделы 10–15 журнала)
читают файлы **без `--tag` и без `_v2`** (`CNYRUBF_train.csv`/`_test.csv`
— baseline с узкими барьерами, раздел 7 журнала) и **не** поддерживают
`--tag` в коде. Они не участвуют в получении финального числа — их роль
была задать вопрос («модель сложнее — лучше?», «дело в переборе?»,
«есть ли дрейф во времени?»), а не собрать итоговый пайплайн. Файлы
`CNYRUBF_train.csv`/`_test.csv` были удалены при уборке (см. журнал
2026-09-01) — чтобы перезапустить любой из них, сначала пересоздать
baseline без тега:
```bash
.venv/bin/python -m scripts.build_dataset --root CNYRUBF   # без --tag
.venv/bin/python -m scripts.train_baseline_model --root CNYRUBF      # раздел 10 журнала
.venv/bin/python -m scripts.train_catboost_model --root CNYRUBF      # раздел 11-12 журнала
.venv/bin/python -m scripts.tune_catboost_model --root CNYRUBF       # раздел 13-14 журнала
.venv/bin/python -m scripts.analyze_test_subperiods --root CNYRUBF   # раздел 15 журнала
```

### 2.7 Шорт-сторона и совместная стратегия лонг+шорт (раздел 25 журнала)

Шорт — это ОТДЕЛЬНАЯ разметка (`side=-1` в `processing/labeling.py`, зеркально
к лонгу — не разворот вероятности лонговой модели, барьеры асимметричны).
`build_dataset.py` не умеет `--side`, поэтому для шорта шаги 2-4 пайплайна
раздела 1.6 запускаются вручную по отдельности:

```bash
.venv/bin/python -m scripts.build_labels --root CNYRUBF --tag _w4s --side -1 \
    --horizon-bars 80 --tp-vol-mult 4.0 --sl-vol-mult 2.0
.venv/bin/python -m scripts.build_split --root CNYRUBF --tag _w4s
.venv/bin/python -m scripts.build_derived_features --root CNYRUBF --tag _w4s
```

Даёт `CNYRUBF_train_w4s_v2.csv` / `CNYRUBF_test_w4s_v2.csv` — те же бары
(`_bars_features.csv` из 1.6, шаг 1), что и у лонга, просто с зеркальной
разметкой TP/SL.

Затем совместная стратегия:
```bash
.venv/bin/python -m scripts.backtest_long_short --root CNYRUBF
```
* **Файл:** `scripts/backtest_long_short.py`. По умолчанию — walk-forward
  внутри train (5 окон), печатает раздельно «только лонг» / «только шорт» /
  «лонг+шорт» (одна позиция за раз, хронологически более ранний сигнал
  побеждает независимо от стороны). Test не открывает.
* **Test — один раз, явным флагом:**
  ```bash
  .venv/bin/python -m scripts.backtest_long_short --root CNYRUBF --test
  ```

`scripts/backtest.py` и `scripts/backtest_walkforward.py` тоже умеют шорт
через `--side -1` (доходность считается зеркально), но это одиночная
сторона — совместную лонг+шорт линию считает только `backtest_long_short.py`.

* **Архитектура моделирования — решено (2026-08-30):** пул сырых
  контрактов, без склейки в непрерывный ряд. Диагностика (раздел 1 журнала)
  прогнана на всех 4 сериях и везде указывает на пул — это уже не
  предположение по одной серии, а согласованный результат. Но это
  эвристика по фиксированным порогам, не абсолютное доказательство —
  фиксируется явно при переходе к этапу 1.
  **Важно про признаки контракта:** raw contract-id (тикер/figi) —
  **не** годится как категориальный признак, даже на одном инструменте.
  Контракт живёт ограниченное время и исчезает после экспирации — при
  выходе в продакшн модель встретит contract-id, которого не было в
  обучении (unseen category), и не сможет его использовать. Вместо
  identity контракта нужны **структурные признаки положения в
  ролл-цикле**, которые переносятся с одного контракта на другой:
  `days_to_expiration` (или нормализованное 0..1 от жизни контракта),
  ранг контракта (ближний/второй/третий), доля объёма относительно
  типичной кривой концентрации (см. раздел 1 журнала). Отдельная модель на
  инструмент (Этапы 1–4) в `root_symbol` не нуждается — он понадобится,
  только если/когда дойдём до единой модели на несколько инструментов
  сразу, и то в паре со сравнимыми между рынками величинами (проценты,
  а не абсолютные рубли).
* **Бары по обороту (dollar bars) — решено заранее, до реализации
  (2026-08-30):** при построении баров (вероятно, часть Этапа 1) бар
  **не должен переходить через выходные** — иначе на неликвидном
  контракте один бар склеит пятницу с понедельником и создаст
  искусственную асимметрию длительности бара по дням недели. Решение:
  1) фильтр по официальному календарю торговых сессий (внебиржевые
  свечи по выходным исключаются явно), 2) бар принудительно закрывается
  на границе торгового дня, даже если порог по обороту не набран.
  **Проверено на данных futures-lab (2026-08-30):** в `futures_candles`
  тот же артефакт есть и здесь — 79 222 свечи в субботу и 66 152 в
  воскресенье (~2.2% от 6.58М), при том что FORTS в воскресенье в
  принципе не торгуется. Открытый вопрос про календарь FORTS —
  **закрыт, см. раздел 3 журнала.** Итоговое решение: граница бара — разрыв
  между соседними свечами > `GAP_THRESHOLD_MINUTES = 180` (см.
  `db/calendar.py`), не даты/часы сессии. Клиринг (короткий, симметричен
  по дням недели) закрывать бар не должен — под правило и так не
  попадает, порог 180 мин заведомо больше клиринговых пауз (~5-15 мин) и
  меньше настоящих межсессионных разрывов (от ~430 мин).
* **Этап 1 — CNYRUBF:** разбор базиса (курс + разница ставок ЦБ). Начато,
  см. раздел 5 журнала — загрузка вспомогательных данных.
* **Этап 2 — BR:** контанго/бэквордация, влияние мировых цен на нефть.
* **Этап 3 — IMOEXF:** риск на рынок целиком.
  **Кандидат на будущее (2026-08-30):** у IMOEXF тоже есть вечный
  фьючерс на MOEX (`IMOEXF`-перпетуал, второй по ликвидности после
  `CNYRUBF`-перпетуала — раздел 2 журнала), можно повторить сравнение
  "конвергенция vs funding rate" и на индексном активе, не только на
  валютном. Не начато, просто зафиксировано, чтобы не забыть идею.
* **Этап 4 — SBERF:** анализ фьючерса на отдельную акцию.
* **Этап 5 — вечные фьючерсы MOEX (CNYRUBF-перпетуал):** funding rate

* **Этап 6 — криптовалюты-перпетуалы:** 5 инструментов (Bitcoin, Ethereum,

## 4. 📚 Литература

* **Marcos López de Prado — «Advances in Financial Machine Learning» (2018).**
  Фундаментальный источник методов для финансового ML: Triple Barrier,
  Purged K-Fold с embargo, веса по uniqueness/concurrency, meta-labeling,
  MDA по кластерам признаков. Перечитать те главы, которые применяем в
  futures-lab по умолчанию (см. CLAUDE.md).
* **John C. Hull — «Options, Futures, and Other Derivatives».** Классическая
  теория самих фьючерсов: базис, contango/backwardation, cost-of-carry
  (стоимость хранения для товаров, разница ставок для валюты), конвергенция
  цены к экспирации. Отвечает на вопрос «что вообще должно происходить с
  базисом», до того как смотреть, что происходит на самом деле.
* **Ernest P. Chan — «Algorithmic Trading» / «Quantitative Trading».**
  Практическая инженерия: как строить непрерывный ряд из цепочки
  фьючерсных контрактов (back-adjustment, ratio-adjustment вместо наивной
  склейки) и какие артефакты создаёт каждый способ. Самый прицельный
  источник под вопрос «склейка или пул контрактов».
* **Larry Harris — «Trading and Exchanges».** Микроструктура рынков —
  откуда берётся ликвидность, почему у дальних контрактов объём тонкий.
  Пригодится для диагностики концентрации объёма по времени до экспирации.

## 5. Мысли для статьи

1. **Приоритет подготовки данных над моделью в финансовом ML:**
   * **Сырые свечи «в лоб» не работают:** без нормализации и масштабирования признаков модель учит случайный шум.
   * **Целостность рядов:** критично отсутствие пропусков и аномалий (например, пауза торгов на Мосбирже в 2022 г. ломает обучение).
   * **Альтернативные бары (де Прадо):** стандартные тайм-бары (5м) уступают барам по объёму, объёму в валюте или тикам.
   * **Ключевой инсайт:** если данные сформированы, очищены и размечены правильно, обучение модели и получение результата превращается в стандартную инженерно-техническую задачу.
